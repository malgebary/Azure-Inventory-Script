# Sample Output (fabricated demo data)

> **None of the data in this folder is real.** It was generated by
> [`../New-DemoDependencyData.ps1`](../New-DemoDependencyData.ps1) to show the exact
> shape of the reports the main script produces — especially the dependency reports,
> which only populate when VM Insights / Application Insights are enabled in the target
> environment. It is safe to read and share as an example.

These files mirror the output of `AzureA2AInventory.ps1`.

## Scenario modeled

A classic **3-tier application** plus supporting infrastructure:

```
vm-web-01 / vm-web-02  --(8080)-->  vm-app-01  --(1433)-->  vm-sql-01
        \                               |
         \--(53 DNS, 88 Kerberos)-->  vm-dc-01  <--(389 LDAP, 88)--/
```

## How to read `completeness-reconciliation.csv`

This is the **"are we capturing everything?"** proof. Each row is a resource type with its
count and the sheet that captures it. Rows where `hasDedicatedSheet` is **False** live
**only** in the catch-all `resources.csv` — these are the easy-to-miss types (here:
private DNS zone VNet links, VM extensions, network watchers, action groups). They're
still fully captured; they just don't have their own focused sheet.

`completeness-summary.json` reconciles the numbers: when `countsReconcile` is `true`, the
row count in `resources.csv` matches the total resource count from Azure Resource Graph
**exactly** — mathematical proof that nothing was dropped.

## How to read `app-insights-dependencies.csv`

Each row = one type of outbound call an app makes to a backend.

- **`ai-storefront-prod`** depends on: a SQL DB (`StorefrontDb`, ~182k calls — its
  heaviest dependency), an external payments API (`api.payments.contoso.com`, ~211ms —
  slow + external), a blob storage account, and a Service Bus queue.
- **`ai-identity-prod`** depends on: the Entra token endpoint
  (`login.microsoftonline.com`) and a Key Vault (`kv-prod`).

**Migration takeaway:** the storefront app cannot move alone — its SQL DB, storage,
queue, and the external payments API must all be accounted for in the same
migration wave.

## A note on DB → storage

Database-to-storage relationships show up in **`storage-links.csv`** when they are
**configured**. In the sample, the first two rows are exactly this:

- `sql-prod/Default` (`microsoft.sql/servers/auditingsettings`) → **SQL auditing** writing
  to the `stprodbackups` storage account.
- `sql-prod/StorefrontDb` (`...databases/vulnerabilityassessments`) → **VA scans** writing
  to `stprodbackups`.

**Live PaaS database-to-storage traffic is not captured** (Azure SQL / Managed Instance
internals aren't observable). See the "Storage relationships" and "Coverage & limitations"
sections in the top-level README for the full breakdown.
